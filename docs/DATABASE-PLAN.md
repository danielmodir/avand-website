# طرح دیتابیس توجیبی (پیشنهاد — منتظر تأیید)

> این سند از روی **کد واقعی دمو** (`frontend/demo/`) و سندهای `docs/` درآمده.
> هنوز اجرا نشده؛ بعد از تأیید شما، `database/migrations/` بر اساسش بازنویسی می‌شه.
> دیتابیس: MySQL 8.0.16+، همه‌چیز `utf8mb4`.

## ۱. امکاناتی که الان در برنامه هست (و داده می‌خوان)

| بخش | داده‌هایی که الان نگه داشته می‌شه |
|---|---|

| پروفایل | نام، نام خانوادگی، نام کاربری، شناسه‌ی عمومی (مثل `DANI8523`)، ایمیل، تلفن، جنسیت، تاریخ تولد، عکس؛ آمار (کار انجام‌شده، تعداد عادت، چک‌این) |
| تنظیمات | زبان، اعلان روشن/خاموش، شروع هفته، برچسب منوی افزودن، تقویم اصلی، تقویم‌های فعال (شمسی/میلادی/قمری)، تم |
| میزکارها (مدیریت) | روشن/خاموش بودن میزکار «برنامه‌ریزی» و «پریود» |
| تسک | عنوان، دسته، توضیح، عکس (حداکثر ۳)، پین، انجام‌شده / انجام‌نشده (ضربدر قرمز)، ریزتسک‌ها، یک‌روزه یا بازه (شروع + ددلاین)، تکرار (هر چند روز / روزهای هفته)، یادآور (ساعت مشخص / هر چند ساعت + متن) |
| عادت | عنوان، تاریخ شروع، تکرار، یادآور، روزهای انجام‌شده، روزهای ردشده |
| رویداد | عنوان، یک‌روزه یا بازه، تکرار، یادآور |
| ارتباط‌ها (دوستان) | درخواست، قبول/رد، حذف، بلاک/آنبلاک، جستجو با نام کاربری یا تلفن، لینک دعوت |
| پریود | فعال بودن، نمایش روی تقویم، مرحله‌ی کوئیز، تاریخ شروع آخرین دوره، طول چرخه، طول دوره |
| فروشگاه قابلیت‌ها | قابلیت‌ها با سه حالت: قابل‌روشن‌کردن / قفل / پریمیوم (فعلاً خالی) |
| محتوای قابل‌ویرایش ادمین | متن «درباره‌ی ما» به دو زبان؛ حریم خصوصی و شرایط استفاده (هنوز نوشته نشده) |
| مناسبت‌ها | فایل ثابت JSON — **جدول لازم نداره** |

## ۲. مشکلاتی که در طرح فعلی پیدا کردم (باید درست بشن)

1. **تسک تکراری فقط یک «انجام شد» داره.** اگه تسکی هر روز تکرار بشه و امروز تیکش بزنید، همه‌ی روزها تیک می‌خورن. ← وضعیت انجام باید **برای هر روزِ وقوع جدا** ثبت بشه (جدول `task_occurrences`).
2. **روزهای انجام عادت به‌صورت یک لیست JSON ذخیره می‌شه.** اگه دو دستگاه هم‌زمان تیک بزنن، یکی تغییر اون یکی رو پاک می‌کنه؛ آمار و «زنجیره‌ی روزها» هم سخت حساب می‌شه. ← هر روز یک ردیف (`habit_logs`).
3. **ریزتسک‌ها فقط متن + تیک هستن**، ولی شما خواستید ریزتسک «هیچ فرقی با تسک معمولی نکنه» (بازه، منو، انتخاب). ← ریزتسک = خودِ تسک با `parent_id` (فقط یک سطح).
4. **عکس‌ها به‌صورت متن base64 داخل دیتابیس می‌رن.** دیتابیس سنگین و کند می‌شه. ← فایل روی فضای ذخیره‌سازی، فقط مشخصاتش در جدول `attachments`.
5. **دسته‌بندی متن آزاده** (هر بار تایپ). ← جدول `categories` برای هر کاربر.
6. **داده‌ی پریود اطلاعات سلامتیه** و الان کنار بقیه بدون محافظت اضافه نگه داشته می‌شه. ← جدول جدا + **رمزنگاری** مقادیر.
7. **حذف روی یک دستگاه به بقیه‌ی دستگاه‌ها نمی‌رسه** (برنامه چنددستگاهیه). ← «حذف نرم» با `deleted_at` + همگام‌سازی بر اساس `updated_at`.
8. **جستجو با شماره تلفن** یعنی هر کس شماره‌ی شما رو داشته باشه پیداتون می‌کنه. ← تنظیم «قابل پیدا شدن با تلفن» که پیش‌فرض خاموشه.
9. **شناسه‌ی عمومی (`DANI8523`) سمت مرورگر ساخته می‌شه** و یکتا بودنش تضمین نیست. ← ستون یکتا در دیتابیس.
10. **ادمین تعریف نشده**؛ هر کسی که بخش مدیریت رو ببینه می‌تونه متن «درباره‌ی ما» رو عوض کنه. ← نقش کاربر + ثبت تغییرات ادمین.

## ۳. جدول‌های پیشنهادی

### حساب و امنیت
| جدول | کارش | نکته‌ی امنیتی |
|---|---|---|
| `users` | ایمیل، هش رمز، نقش (`user` / `admin`)، وضعیت (فعال/مسدود)، تأیید ایمیل | رمز با **Argon2id** (یا bcrypt)، هیچ‌وقت خود رمز |
| `oauth_accounts` | اتصال حساب گوگل (provider + شناسه‌ی گوگل) | فقط شناسه، نه توکن گوگل |
| `sessions` | هر ورود روی هر دستگاه: هش توکن، نام دستگاه، انقضا، آخرین استفاده | فقط هش توکن؛ «خروج از همه‌ی دستگاه‌ها» ممکن |
| `auth_tokens` | لینک تأیید ایمیل و فراموشی رمز | هش‌شده، یک‌بارمصرف، انقضای کوتاه |
| `auth_events` | لاگ ورود موفق/ناموفق، تغییر رمز، خروج | برای محدود کردن تلاش‌های ورود و پیگیری نفوذ |

### کاربر
| جدول | کارش |
|---|---|
| `profiles` | نام، نام کاربری (یکتا)، شناسه‌ی عمومی (یکتا)، تلفن، جنسیت، تاریخ تولد، عکس |
| `user_settings` | زبان، تقویم اصلی، تقویم‌های فعال، شروع هفته، اعلان، برچسب منو، تم، **قابل پیدا شدن با تلفن** |
| `user_desktops` | کدوم میزکار روشنه و به چه ترتیبی (برنامه‌ریزی، پریود، و میزکارهای آینده) |

### برنامه‌ریزی
| جدول | کارش |
|---|---|
| `categories` | دسته‌های هر کاربر (نام، رنگ) |
| `tasks` | تسک‌ها و ریزتسک‌ها (`parent_id`)، بازه‌ی شروع/ددلاین، پین، ترتیب، تکرار، یادآور |
| `task_occurrences` | وضعیت هر روزِ یک تسک تکراری: انجام‌شده / انجام‌نشده |
| `habits` | عادت‌ها، تاریخ شروع، تکرار، یادآور |
| `habit_logs` | هر روز یک ردیف: انجام‌شده / ردشده |
| `events` | رویدادها، یک‌روزه یا بازه، تکرار، یادآور |
| `attachments` | مشخصات فایل عکس‌ها (مسیر، نوع، حجم، صاحب) — خود فایل بیرون از دیتابیس |

### اجتماعی
| جدول | کارش |
|---|---|
| `connections` | هر جفت کاربر یک ردیف: در انتظار / پذیرفته / بلاک، و این‌که کی درخواست داده |
| `invites` | لینک‌های دعوت و این‌که کی با لینک کی ثبت‌نام کرده |

### پریود (جدا و رمزنگاری‌شده)
| جدول | کارش |
|---|---|
| `period_profiles` | طول چرخه، طول دوره، نمایش روی تقویم، وضعیت کوئیز — مقادیر **رمزنگاری‌شده** |
| `period_cycles` | تاریخ شروع هر دوره (برای پیش‌بینی دقیق‌تر از روی تاریخچه) — رمزنگاری‌شده |

### اعلان و یادآور
| جدول | کارش |
|---|---|
| `push_subscriptions` | اشتراک اعلان هر دستگاه (وب / اندروید) |
| `notification_log` | چه یادآوری کی فرستاده شد (جلوگیری از ارسال تکراری) |

### فروشگاه و محتوا
| جدول | کارش |
|---|---|
| `features` | فهرست قابلیت‌های فروشگاه (کلید، نوع: رایگان/قفل/پریمیوم، قیمت) |
| `user_features` | قابلیت‌های هر کاربر (روشن/خاموش، از کجا گرفته: رایگان/خرید) |
| `purchases` | پرداخت‌ها (درگاه، کد پیگیری، مبلغ، وضعیت) — **وقتی فروش واقعاً راه افتاد** |
| `app_content` | متن‌های قابل‌ویرایش (درباره‌ی ما، حریم خصوصی، شرایط) به دو زبان |
| `admin_audit_log` | هر تغییری که ادمین داده: کی، چی، کِی |

جمعاً حدود **۲۴ جدول**؛ ۴ جدول آخرِ فروشگاه/پرداخت می‌تونن تا زمان راه‌اندازی فروش صبر کنن.

## ۴. قواعد امنیت و نظم (برای همه‌ی جدول‌ها)

- **هر ردیف صاحب داره** (`user_id`) و API همیشه با شرط «مال همین کاربر» می‌خونه/می‌نویسه.
- **فقط کوئری پارامتری** (جلوی SQL Injection).
- **دو کاربر دیتابیس:** یکی برای برنامه (فقط خواندن/نوشتن داده) و یکی فقط برای migration (ساخت/تغییر جدول).
- **اتصال رمزنگاری‌شده (TLS)** بین سرور و دیتابیس، **بکاپ رمزنگاری‌شده** روزانه.
- **رمزنگاری در سطح برنامه** برای داده‌ی پریود (AES-256-GCM)، کلید بیرون از دیتابیس.
- **حذف حساب واقعی:** با حذف کاربر، همه‌ی داده‌هاش پاک می‌شه (حق کاربر).
- **پاک‌سازی خودکار** نشست‌ها و توکن‌های منقضی.
- **محدودیت تلاش** برای ورود، ثبت‌نام، جستجوی دوست و فراموشی رمز.
- همه‌ی جدول‌ها: شناسه‌ی UUID، `created_at`، `updated_at`، و برای داده‌های همگام‌شونده `deleted_at` + `version`.
- داده‌ی شخصی کمینه: فقط چیزی که واقعاً استفاده می‌شه.

## ۵. تصمیم‌هایی که باید شما بگیرید

1. **روش ورود:** ایمیل + رمز و گوگل کافیه، یا **ورود با شماره موبایل و کد پیامکی** هم می‌خواید؟ (در ایران رایجه؛ سرویس پیامک لازم داره)
2. **تسک تکراری:** تأیید می‌کنید هر روزش جدا تیک بخوره؟
3. **ریزتسک:** فقط یک سطح (تسک → ریزتسک) یا ریزتسکِ ریزتسک هم؟
4. **محل عکس‌ها:** روی خود سرور یا فضای ابری (مثلاً ابرآروان)؟
5. **فروشگاه و پرداخت:** الان طراحی بشه یا بعداً؟
6. **اعلان روی گوشی:** کدوم سرویس؟ (Firebase در ایران مشکل داره؛ گزینه‌های داخلی مثل پوشه/نجوا هست)
7. **پریود:** رمزنگاری و جدا بودنش تأیید؟
