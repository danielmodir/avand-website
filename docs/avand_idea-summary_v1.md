# آوند (Avand) — خلاصه‌ی ایده

> وضعیت: مرحله‌ی برشش فکری / پخته‌کردن ایده — هنوز طراحی نهایی، معماری فنی یا MVP قطعی نشده.

---

## ۱. ایده‌ی کلی

اپلیکیشن توسعه‌ی فردی مبتنی بر **زمان و تقویم**، قابل استفاده **آفلاین و آنلاین**، با قابلیت **شخصی‌سازی کامل** بر اساس علایق، اهداف و نیازهای کاربر. در حالت آنلاین امکان ارتباط با دیگر کاربران هم وجود دارد.

---

## ۲. ماژول‌های اصلی (Core)

| ماژول | توضیح |
|---|---|
| **Task** | کار مربوط به یک روز مشخص؛ اگر انجام نشود، خودکار به روز بعد منتقل نمی‌شود — فقط وضعیت «انجام‌نشده» ثبت می‌ماند. |
| **Habit** | کار تکرارشونده با تیک روزانه؛ خروجی به‌صورت درصد و نمودار پیشرفت. |
| **Challenge** | نسخه‌ی از پیش‌طراحی‌شده و زمان‌بندی‌محدود از Habit (مثلاً ترک سیگار)؛ در ارتباط مستقیم با Habit. |
| **Calendar / Planning** | تقویم مرکزی که با سایر بخش‌ها در ارتباط است. |
| **Event** | رویدادهای زمان‌دار (کلاس، جلسه و…)؛ برای رویدادهای آنلاین امکان قراردادن لینک وجود دارد. |
| **Journal** | نوشتن وضعیت روزانه + نمره‌دهی به Mood، Discipline و وضعیت کلی روز. |
| **Reports / Charts** | گزارش و نمودار روزانه/هفتگی از میزان انجام Task و Habit. |
| **Notification** | قابل شخصی‌سازی برای همه‌ی ماژول‌ها (زمان و نوع دست کاربر است). |
| **AI / Chatbot** | فاز اول: ورودی زبانی برای مدیریت آیتم‌ها. فاز بعد: تنظیم خودکار موارد (مثل نوتیف) صرفاً با دستور کاربر. |
| **ارتباط با دیگران (Social)** | دیدن وضعیت/نمره‌ی دیگران؛ فعلاً ایده‌ای کاملاً خام. |

---

## ۳. Category — دو مدل

### مدل ۱: Category شخصی (Custom)
کاربر آزادانه یک پوشه می‌سازد (شبیه ساختار Project در Claude/ChatGPT) و هر آیتمی (Task، Habit، Event و…) که بخواهد زیرش قرار می‌دهد.

### مدل ۲: Tools (ابزارها)
ماژول‌های از پیش‌ساخته و تخصصی — مثال: **Trading**
- نمایش قیمت و نمودار، متصل به TradingView
- نوتیفیکیشن سفارشی داخل خودِ اپ (نه از طریق TradingView) — مثلاً «وقتی قیمت به X رسید» یا در زمان مشخص
- برخی آیتم‌های داخل هر Tool **پیش‌فرض و قفل‌شده‌اند** (غیرقابل‌حذف) — مثلاً Eventهای اقتصادی مهم مانند تاریخ تصمیم نرخ بهره‌ی آمریکا
- برخی آیتم‌ها **اختیاری‌اند** و کاربر می‌تواند اضافه/حذف کند

---

## ۴. Tool Store (فروشگاه ابزار)

فروشگاهی داخل اپ برای Tools:
- برخی Tool رایگان، برخی پولی
- کاربر خرید می‌کند و Tool به بخش Tools شخصی‌اش اضافه می‌شود

### مدل پرداخت
- فعلاً: **پرداخت درون‌برنامه‌ای (In-App Purchase)**
- آینده: افزودن **پرداخت از طریق گوگل (Google Play Billing)**

---

## ۵. نقشه‌ی زمانی پلتفرم‌ها

1. فاز اول: اپلیکیشن اندروید
2. فاز بعد: نسخه‌ی iOS
3. فاز بعد: وب‌سایت معرفی محصول (Landing Page)

## ۷. ریسک‌ها و نکات باز (Open Questions)

- **Overscoping MVP**: تعداد ماژول‌ها برای نسخه‌ی اول بسیار زیاد است؛ نیاز به فاز‌بندی (Phased Rollout) دارد.
- **پرداخت دوگانه**: مدیریت هم‌زمان In-App Purchase و Google Play Billing نیازمند طراحی فنی/قانونی دقیق است.
- **چندپلتفرمی‌شدن**: معماری Backend/API باید از ابتدا مستقل از پلتفرم طراحی شود.
- **حریم خصوصی در بخش Social**: نمایش وضعیت/نمره‌ی افراد به یکدیگر می‌تواند هم انگیزه‌بخش و هم فشارزا باشد — نیاز به تصمیم درباره‌ی حریم خصوصی پیش‌فرض دارد.
- **مرز Task/Event**: باید دقیق‌تر مشخص شود (احتمالاً: Event = زمان‌دار با لوکیشن/لینک، Task = کار بدون لزوم زمان دقیق).
