# آوند (Avand) — فاز ۵: انتخاب استک فنی

> وضعیت: هر سه تصمیم اصلی فاز ۵ (فریم‌ورک موبایل، بک‌اند/دیتابیس، نیاز به API اختصاصی) نهایی شد.

---

## ۱. زمینه‌ی تصمیم‌گیری

قبل از انتخاب استک، شرایط زیر در نظر گرفته شد:

| عامل | وضعیت |
|---|---|
| سطح تجربه‌ی برنامه‌نویسی | تجربه با HTML/CSS، کمی JS، C/C++، و Python (بدون تجربه‌ی بک‌اند) |
| نیروی انسانی | توسعه توسط دنیل، با کمک Claude؛ احتمال استخدام برنامه‌نویس در آینده |
| اولویت اصلی فعلی | سرعت رسیدن به MVP (حتی با پذیرفتن محدودیت‌های بعدی) |

---

## ۲. تصمیم‌های نهایی

### ۲.۱ فریم‌ورک موبایل: **React Native (با Expo)**

| گزینه | نمره از ۱۰ | دلیل |
|---|---|---|
| **React Native** | ۸ | با JavaScript کار می‌کنه (آشنایی نسبی وجود داره)؛ چون پرکاربردتر از Flutter/Dart هست، ابزارهای AI (از جمله Claude) پشتیبانی و خروجی بهتری براش دارن؛ جامعه‌ی بزرگ و استخدام آینده راحت‌تر |
| Flutter | ۶ | زبان Dart کاملاً جدید و ناآشناست؛ عملکرد و یکپارچگی UI عالی، ولی مسیر شروع سریع با کمک AI سخت‌تره |

**Expo** به‌عنوان لایه‌ی راه‌اندازی روی React Native انتخاب شد چون راه‌اندازی اولیه و توسعه‌ی تک‌نفره رو ساده‌تر می‌کنه.

### ۲.۲ بک‌اند و دیتابیس: **Firebase**

| گزینه | نمره از ۱۰ | دلیل |
|---|---|---|
| **Firebase** (Firestore + Auth + Cloud Functions) | ۹ | بدون نیاز به مدیریت سرور؛ راه‌اندازی سریع؛ اتصال مستقیم از اپ بدون نیاز به API جدا؛ مناسب توسعه‌ی تک‌نفره‌ی MVP |
| Node + PostgreSQL | ۴ | انعطاف و کنترل بیشتر برای داده‌های رابطه‌ای، ولی نیاز به مدیریت سرور + نبود تجربه‌ی بک‌اند = کندی در رسیدن به MVP |

### ۲.۳ نیاز به API اختصاصی: **فعلاً خیر**

در فاز MVP، اپ مستقیماً از طریق Firebase SDK با بک‌اند صحبت می‌کنه؛ نیازی به ساخت و نگه‌داری یه API جداگانه نیست.

---

## ۳. ریسک ثبت‌شده (Open Risk)

**تعارض بین سرعت فعلی و معماری بلندمدت:**
مدل داده‌ی آوند (Task ↔ Category ↔ Tool ↔ Habit ↔ Challenge) نسبتاً رابطه‌ایه، در حالی که Firestore یه دیتابیس NoSQL هست. این تصمیم آگاهانه گرفته شد چون اولویت فعلی سرعت رسیدن به MVP هست، اما:

> در فازهای بعدی (به‌خصوص با اضافه‌شدن Tool Store و روابط پیچیده‌تر بین ماژول‌ها)، ممکنه نیاز به مهاجرت از Firestore به یه بک‌اند اختصاصی (مثل Node + PostgreSQL) پیش بیاد.

این ریسک آگاهانه پذیرفته شد و باید در فازهای بعدی (توسعه، زیرساخت) دوباره بررسی بشه.
